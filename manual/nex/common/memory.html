3. Memory Management

3.1. Changing the Memory Allocator [Recommended]

The NEX library frequently performs dynamic memory allocation. Use the MemoryManager::SetBasicMemoryFunctions() function to set a memory allocator prepared in the application. The NEX library allocates memory using the standard malloc() and free() functions when no memory allocator has been set. We recommend using an application-specific memory management mechanism in the product.

If a memory allocator is specified, it is used by the NEX library for dynamic memory allocation, and by the application when new occurs for public classes that inherit RootObject. (If a class does not inherit RootObject, this will be noted in its description. )

3.2. libcurl Initialization [Required]

The NEX library uses the libcurl library to communicate with the game server and storage server. Initialize libcurl by having the application call one of the following functions.

  • curl_global_init_mem() (Recommended)
  • curl_global_init()

Note that these functions are not thread-safe. For more information, see the libcurl manual.

3.3. Changing the libcurl Memory Allocator [Recommended]

A single allocator can be set for the entire libcurl. libcurl allocates memory using the standard malloc() or free() when no memory allocator has been set.

We recommend using an application-specific memory management mechanism in the product. Specify a thread-safe memory allocator as a proprietary memory management mechanism regardless of the NEX thread mode. The curl_global_cleanup() function must be run before releasing the memory allocator region.

The following example shows how to replace the memory allocator using nn::mem:StandardAllocator.

Code 3.1. Using nn::mem:StandardAllocator
#include <cstring>
#include <stdint.h>
#include <curl/curl.h>
#include <nn/mem.h>

namespace
{
    nn::mem::StandardAllocator s_curlHeapHandle;
    uint8_t* s_pCurlMemory = NULL;
    uint8_t* s_pCurlMemory = NULL;
    // Memory size for libcurl
    // Around 750 KB of memory are required when using DataStore, and around 275 KB are required when not using DataStore.
    // The amount of memory used in Win is different from that in NX.
    const size_t CURL_MEMORY_SIZE = 1024 * 1024;
}

// Memory allocator helper function for CURL.
void *CurlMallocCallback(size_t size)
{
    return s_curlHeapHandle.Allocate(size);
}

void CurlFreeCallback(void *ptr)
{
    s_curlHeapHandle.Free(ptr);
}

void *CurlReallocCallback(void *ptr, size_t size)
{
    return s_curlHeapHandle.Reallocate(ptr, size);
}

void *CurlCallocCallback(size_t nmemb, size_t size)
{
    void *ptr = CurlMallocCallback(nmemb * size);
    memset(ptr, 0, nmemb * size);
    return ptr;
}

char *CurlStrdupCallback(const char *str)
{
    void* pNewString = CurlMallocCallback(strlen(str) + 1);

    memcpy(pNewString, str, strlen(str) + 1);

    return static_cast<char*>(pNewString);
}

bool CurlGlobalInitMem()
{
    s_pCurlMemory = new uint8_t[CURL_MEMORY_SIZE];
    s_curlHeapHandle.Initialize(s_pCurlMemory, CURL_MEMORY_SIZE);

    // Set the memory allocator for CURL and initialize.
    // Regardless of the NEX thread mode, it has to be a thread-safe memory allocator.
    // Also includes curl_global_init() processing.
    return curl_global_init_mem(CURL_GLOBAL_ALL,
        CurlMallocCallback,
        CurlFreeCallback,
        CurlReallocCallback,
        CurlStrdupCallback,
        CurlCallocCallback) == CURLE_OK;
}

// Call instead of curl_global_cleanup.
void CurlGlobalCleanup()
{
    curl_global_cleanup(); // Must be run after NEX finalization is complete because this function is not thread-safe.
                           // In addition, it must be run before the memory region set with curl_global_init_mem() is released.

    s_curlHeapHandle.Finalize();
    delete[] s_pCurlMemory;
    s_pCurlMemory = NULL;
}

3.4. Preparing for Memory Exhaustion [Required]

The NEX library includes code that presumes dynamic memory allocation always succeeds. For this reason, make sure that your implementation returns a valid memory address. Specifically, it must be implemented as follows.

  • Shut down the library if you allocate more memory than expected.
  • Allocate a memory parachute of several kilobytes beforehand, enough to run until the library can be shut down normally. If an allocation fails, deallocate the memory parachute. Then shut down the library.
  • Have plenty of memory available beforehand. (Perform enough debugging to make sure that there is enough memory if the communication environment worsens, or in other scenarios.)

3.5. Thread Safety Considerations

You must use a thread-safe allocator when using the NEX API from multiple threads because memory is also allocated from multiple threads. For more information, see 4.1.

3.6. Using the NEX Allocator From Your Application

You can use the allocator specified in MemoryManager::SetBasicMemoryFunctions by calling new from a class that inherits RootObject.

Code 3.2. Using the NEX Allocator
// Because NATTraversalClient inherits from RootObject,
// The following code uses the allocator configured by MemoryManager::SetBasicMemoryFunctions.
NATTraversalClient* pNATTraversalClient = new NATTraversalClient();
delete pNATTraversalClient;

3.7. Guide for Memory Needed for Server Features

The following recommendations apply when nn::nex::Core::ThreadModeSafeTransportBuffer is specified for the thread mode. However, the guide for memory required when using the NEX server functions differs according to the functions used and how often they are called.

  • During asynchronous processing NgsFacade::Login(): Uses a maximum of approximately 671 KB.
  • After logging in to the game server without running asynchronous processing while continuously calling only Scheduler::Dispatch() in a static state: Approximately 656 KB.
  • Matchmaking: When the auto matchmaking feature is used without calling asynchronous processing multiple times simultaneously, approximately 122 KB is added to the memory required when in a static state whether you are the owner or host.
  • Ranking: Approximately the amount obtained by RankingClient::GetRanking(). When 20 are obtained, approximately 88 KB is added to the memory used when in a static state. When 255 are obtained, about 197 KB of memory is added.

Then, in addition to this memory, allocate about 20 percent extra memory for emergencies. We also recommend performing immediate logout processing when more memory than anticipated is consumed.

3.8. NX Socket Buffer Usage

Socket buffers that are 96*1024 bytes in size are required to connect to a game server. If several users are logged in at the same time, the socket buffer size must be multplied by the number of users. You need a socket buffer that is DataStoreClient::GetHttpSendSocketBufferSize() + DataStoreClient::GetHttpRecvSocketBufferSize() in size for each connection to the storage server when using the DataStore storage server.

3.9. Packet Buffer Memory Management

Within NEX memory allocation, the packet buffer manager performs memory management of packet buffers used in real-time communication.

The packet buffer manager is a feature that allocates a dedicated memory pool (the packet buffer pool) as a batch process before starting real-time communication, and then allocates memory from that packet buffer pool according to packet buffer memory allocation requests.

The packet buffer manager used by the packet buffer pool is enabled by default.

Memory for the packet buffer pool is allocated using the same method as other NEX objects.

NEX-wide memory consumption errors caused by transmitting and receiving large packets is prevented because memory for the packet buffer pool is allocated in advance and limited in size.

The packet buffers used with the following communications are not managed with the packet buffer manager but have the same memory management as other NEX objects.

  • Communication with the server
  • Sending and receiving data in excess of the maximum size that the packet buffer manager can allocate (1364 bytes)

Note:

Because transmission of data packets that are large in size is out of the management scope of the packet buffer manager, exercise caution when manually transmitting these packets can have an effect on the system memory of the NEX.

3.9.1. Disabling the Packet Buffer Pool

To manage the memory in the same manner as other NEX objects and bypass the packet buffer pool, set PacketBufferManager::EnablePacketBufferPool() to false.

Change this setting before initiating real-time communication.

This must be set for each initialization of NEX. The set values are maintained until NEX terminates.

Code 3.3 Example of Managing Memory for the Packet Buffer in the Same Way as Other NEX Objects
bool ret = PacketBufferManager::EnablePacketBufferPool(false);
if (! ret)
{
    // This cannot be set during peer-to-peer transmission and will throw an exception if called.
}

3.9.2. Packet Buffer Pool

The packet buffer pool is a memory pool used to allocate memory for real-time communication.

The packet buffer pool is allocated before starting real-time communication and is deallocated when real-time communication stops. Specifically, it is allocated the moment the ConnectivityManager::StartNATSession() or VSocket::Open() function is called and deallocated when the ConnectivityManager::StopNATSession() or VSocket::Close() function is called.

The packet buffer pool is managed by using multiple unit heaps and is used to allocate objects used for managing packets attached to payloads that are not packet payloads. For the payload unit heap, the unit size and number of memory blocks can be customized on the application side. Customize according to the application communication data size.

Packet buffer allocation attempts to allocate memory from the unit heap with the smallest unit size and uses the first unit heap that can be allocated. The packet buffer pool enters a depleted state when it is not possible to allocate the largest possible size unit heap to an object (buffers exceeding 1364 bytes are out of scope for allocation by the packet buffer pool).

The default packet buffer uses a 1364-byte unit heap for payloads, and uses a 300-KB region for the object used in packet management.

3.9.3. Customizing the Unit Heap Configuration

The unit heap configuration for payloads can be set by calling PacketBufferManager::SetUnitHeapParam(). The unit heap for packet management objects will automatically be set internally by NEX in accordance with the unit heap for payloads.

Change the configuration for unit heaps before initiating peer-to-peer communication. This cannot be set during peer-to-peer communication. After the unit heap configuration has been set, the value persists until NEX terminates. There is no need to reset this value on a peer-to-peer session basis.

The unit heap configuration must meet the following requirements.

  • The unit size must be set in multiples of four and be less than or equal to 1364 bytes.
  • It must include a unit heap of the maximum size (1364 bytes).

The largest size unit heap is required for use in increasing the transmission efficiency of packets through bundling and NEX internal transmission. Additionally, ensure that the memory block count is equal to or greater than 64. If this is not enough, increase it.

Note:

  • Take the headers added internally by NEX into consideration when setting the unit size and add 80 bytes to the size you want to set. This should be adjusted to multiples of four.
  • If an illegal unit heap configuration has been set, PacketBufferManager::SetUnitHeapParam() will cause an assertion failure.
Code 3.4 Example of Setting the Unit Heap Configuration
qVector<PacketBufferManager::UnitHeapParam> paramList(3);
// For short size packet use
.paramList[0].unitSize = 128+80; // The additional 80 bytes is in consideration of the header added by NEX
paramList[0].unitNum = 32;
// The main size used in the application plus an additional 64 bytes
paramList[1].unitSize = 500++80; // The additional 80 bytes is in consideration of the header added by NEX.
paramList[1].unitNum = 64;
// Packet size used for packet bundling (using a maximum of 1364 bytes)
paramList[2].unitSize = 1364;
paramList[2].unitNum = 128; // Set the unit number to take as many blocks as possible.
bool ret = PacketBufferManager::SetUnitHeapParam(paramList);
if (! ret)
{
    // This cannot be set during peer-to-peer transmission and will throw an exception if called.
    // If an illegal unit heap configuration has been set this will cause an assertion failure.
}

As shown in the example above, apart from setting the configuration individually with PacketBufferManager::UnitHeapParam, PacketBufferManager::GetSimpleUnitHeapParam() can also be used to get the simple configuration.

PacketBufferManager::GetSimpleUnitHeapParam() sets the size of the packet buffer pool and average transmission data size. Simple structures are calculated to fit in a packet buffer pool for which the memory totals for the unit heaps for the payload and for the packet management objects were specified. Half of the memory used by the unit heap for payloads is allocated as a unit heap the size of the average send data, and the remaining half is allocated as an unit heap of the maximum size (1364). Note that the unit size takes the header attached inside NEX, and the average send data send size is increased by 80 and is revised to a value that is a multiple of 4.

Code 3.5 Example of Setting the Simple Configuration
// The pool size is 500 KB, the average data transmission size is 500 bytes
qVector<PacketBufferManager::UnitHeapParam> param;
bool ret = PacketBufferManager::GetSimpleUnitHeapParam(500*1024, 500, param);
if (! ret)
{
    // This throws an exception if the pool size is too small or if an illegal average data transmission size is defined.
}
else
{
    ret = PacketBufferManager::SetUnitHeapParam(param);
    if (! ret)
    {
        // This cannot be set during peer-to-peer transmission and will throw an exception if called.
        // If an illegal unit heap configuration has been set this will cause an assertion failure.
    }
}

3.9.4. Getting Statistical Information

Statistical information on unit heap memory allocation for the payload can be obtained by calling PacketBufferManager::GetUnitHeapDebugInfo(). This obtains information about the memory blocks used and memory allocation errors. The information can be used as a guideline for setting your unit heap configuration or as a method for checking memory exhaustion status.

NEX checks whether there is enough memory before allocating buffers. When there is not enough, it may be counted as an occurrence of memory exhaustion. For this reason, the count for memory exhaustion occurrences may increase without the peak value of the actual allocated number reaching the maximum.

Note:

When the memory exhaustion occurrence count for the unit heap with the largest unit size increases, set the unit heap structure so that the maximum for the number of memory blocks is increased.

Code 3.6 Example of Verifying the Out of Memory Status of the Packet Buffer
qVector<PacketBufferManager::UnitHeapDebugInfo> debugInfo;
PacketBufferManager::GetUnitHeapDebguInfo(debugInfo);
qVector<PacketBufferManager::UnitHeapDebugInfo>::const_iterator it;
it = debugInfo.begin();
while (it != debugInfo.end())
{
    // Displaying the unit size of each unit heap and the out of memory count
    QLOG(EventLog::Info, NEX_T("unitSize:") << it->unitSize << NEX_T(" outOfMemory:") << it->outOfMemory);
}
