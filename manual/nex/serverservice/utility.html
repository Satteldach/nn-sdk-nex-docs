10. Utilities

This section provides an overview of the utilities available in NEX.

10.1. Utilities Workflow

This is the basic workflow when you use the utilities.

  1. Log in to the game server.
  2. Initialize a service client. For more information, see 10.2.
  3. Use the various utilities.
    • Use a password protected NEX unique ID. For more information, see 10.3.2..
    • Get application settings. For more information, see 10.4.3..
    • Call other functions as needed.
  4. Finalize the service client, and log out from the game server.

10.2. Initializing and Finalizing a Service Client

Initializing and finalizing a service client for the utilities (UtilityClient) involves the same processes as in matchmaking. For more information, see section 4.3.

10.3. NEX Unique ID

The NEX unique ID is a unique ID issued by the game server.

You can get the NEX unique ID with the UtilityClient::AcquireNexUniqueId() or UtilityClient::AcquireNexUniqueIdWithPassword() function. The latter function includes a password to use it when a password is needed. A new NEX unique ID is issued each time one of these functions is called. Both use the same ID system, and they only differ in whether they return a password. To check whether a NEX unique ID is valid and was issued from the server, use the UtilityClient::IsValidNexUniqueId() function.

Note:

NEX unique IDs are not unique across game servers. This is also true for server environments. NEX unique IDs are not guaranteed to be unique between a development environment and a production environment, for example.

10.3.1. Using Password-Free NEX Unique IDs

The rankings features use NEX unique IDs that do not include passwords.

10.3.1.1. Using NEX Unique IDs for Rankings

You can use NEX unique IDs to register scores on a more detailed basis than when using principal IDs alone.

For example, they can be used in situations such as the following.

  • When you want to share the same save data among multiple users and register scores separately for each user.
  • When a single user plays a game using multiple characters, and you want to register scores for each character.

When using NEX unique IDs, get a NEX unique ID the first time a score is ranked, and pass that ID as an argument to each of the ranking functions. The first time a NEX unique ID is obtained, save it in save data and then retrieve it from the save data from then on.

To register scores on the basis of principal IDs, specify nn::nex::INVALID_UNIQUEID (the default value) for the NEX unique ID.

Note:

When using NEX unique IDs issued by the game server, describe how you plan to use them in detail on OMAS, and note the following.

  • When a user deletes save data, there is no longer a way to identify the NEX unique ID that was used. The data remains on the server with no way to be updated or deleted.
  • If the same user repeatedly creates save data, uploads a high score, and then deletes the save data, that user may be in first place in the rankings permanently.
  • For friend rankings, if the local user and the friends of that user upload scores under multiple NEX unique IDs, all of those scores (and not just the high score for that user) are included in the rankings because rankings are retrieved on the basis of principal IDs.

10.3.2. Using Password-Protected NEX Unique IDs

Ranking2 and the MatchmakeReferee feature use password protected NEX unique IDs.

To use password protected NEX unique IDs, first use the UtilityClient::AcquireNexUniqueIdWithPassword() function to get a NEX unique ID and the associated password.

Next, use the UtilityClient::AssociateNexUniqueIdWithMyPrincipalId() function to register the NEX unique ID and password on the server and associate them with a principal ID.

The NEX unique IDs associated with a principal ID are known as associated NEX unique IDs. To associate all of the NEX unique IDs, you can specify a list of NEX unique IDs with a single principal ID. The element added to the top of the list of associated NEX unique IDs is known as the primary associated NEX unique ID.

When the UtilityClient::AssociateNexUniqueIdWithMyPrincipalId() function is called, if NEX unique IDs that were previously associated with that principal ID are not included, any data associated with those NEX unique IDs is deleted. Therefore, NEX unique IDs for which you do not want the associated data to be deleted must be specified in the list every time this function is called, even if those NEX unique IDs were registered at an earlier time.

For example, consider an application that has three pieces of save data, and you want to keep those pieces of save data separate on the server. To do this, first, each time a new piece of save data is created, get a new NEX unique ID from the server. Save this NEX unique ID as part of the save data.

Then, when a certain piece of save data is selected, associate the list of NEX unique IDs for all of the save data that has been created thus far (starting with the NEX unique ID for the selected save data) with the principal ID. This list must include NEX unique IDs that are already registered. Therefore, you must also prepare common save data in addition to the individual pieces of save data. This process must be repeated every time a different piece of save data is selected, not just the first time a piece of save data is selected. Any other features used in this state work on a per-NEX unique ID basis.

Finally, when the save data is deleted, delete the NEX unique ID associated with that save data. Then, to delete any data associated with that deleted NEX unique ID from the server, immediately after, or the next time a piece of save data is selected, associate a list of NEX unique IDs that does not include the deleted NEX unique ID with the principal ID.

The association between a principal ID and an associated NEX unique ID might change due to circumstances outside of the application. If you try to use an associated NEX unique ID after it has been disassociated, you might receive a communication error. For example, if you try to send a Ranking2 score in that state, QERROR(Ranking2, InvalidArgument) will occur.

To avoid this error, the application must call the UtilityClient::AssociateNexUniqueIdWithMyPrincipalId() function every time it logs in to the game server. For more information, see Nintendo Switch Guidelines > 0147.

10.3.2.1. Using NEX Unique IDs With the MatchmakeReferee Feature

With the MatchmakeReferee feature, using password protected NEX unique IDs enables more fine-tuned control of personal statistics than when using principal IDs.

After an associated NEX unique ID has been registered, personal statistics recorded during subsequent processes are recorded using the primary associated NEX unique ID.

When the associated NEX unique ID is deleted, the personal statistics associated with that ID are also deleted.

10.3.2.2. Using NEX Unique IDs in Ranking2

In Ranking2, using password protected NEX unique IDs enables more fine-tuned control of scores and common user data than when using principal IDs.

After an associated NEX unique ID has been registered, subsequent work on scores and common user data for that user can be processed using the NEX unique ID.

Adding an associated NEX unique ID will delete any added scores and common user data when there is no association with a NEX unique ID. When the associated NEX unique ID is deleted, scores and common user data associated with that ID are also deleted.

The existing ranking features previously used password-free NEX unique IDs, but now the ranking features use password protected NEX unique IDs to associate NEX unique IDs with principal IDs. This solves the issue of being able to upload multiple scores to the same rankings by repeatedly creating and deleting save data, amongst other problems.

10.4. Managing Application Settings

NEX saves application settings on the server and allows the application to retrieve those settings from the server.

If you design your application to work using these settings, you can change or update the behavior of the application just by changing the application settings saved on the server instead of having to update the application ROM itself.

10.4.1. Use Cases

Possible use cases for the application settings management feature include the following, for example. In each case, the application saves the threshold values to use on the server, and the client gets those threshold values from the server and uses them.

  • Testing Data Before Upload to the Data Store

    Assume you only want to upload data that meets or exceeds a certain condition. You can save the threshold testing value on the server to limit the number of pieces of data that get uploaded.

  • Player Ratings

    Assume you want to display ratings that represent player skill on the client devices. You can save the threshold values for determining player ratings on the server to update player ratings according to the number of players, or other play conditions.

Contact Nintendo if you are considering use cases other than those listed above.

10.4.2. Application Settings Details

Application settings include the following elements.

Table 10.1. Application Setting Structure
Item Name Description Accepted Values
Setting index Used to switch settings. You can use up to 20 setting indices. An integer between 0 and 19.
Keys Setting key. You can register up to 100 keys for each setting index. A 16-bit non-negative integer.
Value The setting values itself. 32-bit integer.
Description A description of the setting. UTF-8 string.

Using the setting indices allows you to switch between several groups of settings. For example, if you want to have a setting with the same key but different values for each region, you can create a setting index for each region and configure the keys and values accordingly.

Use NMAS or WebAPI to upload and delete application settings. For more information about WebAPI, see 11.7.2. Managing Application Settings.

10.4.3. Getting Settings

To get the application settings from the application, use UtilityClient::GetIntegerSettings() and specify the setting index for which you would like to get settings.

10.4.4. Important Usage Notes

  • To reduce server load, have the application get the settings immediately after logging into the NEX server, and then store those settings in the application and reuse them for a prescribed period of time.
  • If you use the setting indices to separate settings into debugging settings and production settings, make a dedicated debugging menu that must be used to switch the setting indices so that the debugging settings are never used in the production version of the application.
  • Be aware of the following when changing application settings saved on the server.
    • Immediately after the settings are changed, some clients may still be using the old settings while other clients are using the new settings. This depends on when the application retrieves the settings. Make sure that the application does not behave strangely if not all of the clients are using the same settings. For example, use a matchmaking session attribute to ensure that clients using the old settings and clients using the new settings, do not join the same matchmaking session.
