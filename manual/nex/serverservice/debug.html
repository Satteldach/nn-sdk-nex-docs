9. Debug Assistance

9.1. Introduction

The following features are provided to assist you with debugging when you use NEX in the development of your application.

  • Features to record and get the log of the function calls that are issued during communication with the game server. (For more information, see 9.2. Recording a Log of API Calls.)
  • Features to change the functionality of the game server. (For more information, see 9.3. Changing Game Server Functionality.)
  • Features for error simulation. (For more information, see 9.4. Error Simulation.)

The features that can be used from the application to assist in debugging have been left in place only for the sake of compatibility with earlier versions.

Do not use these features from your application. Instead, use them from NMAS (the web system for managing NEX servers).

Following a future server update sometime after 2022-03-01, an error will be returned indicating failure when these features are used from the application. This update will be applied to all environments (development environments and production environments).

The error simulation feature is the only feature available from WebAPI. For more information about WebAPI, see 11.6. Debug Assistance.

Note:

The package does not include the release build version of the DebugClient library.

9.1.1. Initializing and Finalizing Service Clients

The DebugClient initialization and finalization processes are the same as the processes performed for service clients when matchmaking.

9.2. Recording the API Call Log

The game server can record a log of the calls to functions that instigate communication with the game server, and by getting and checking that log you can check the behavior of the application. You can also use this log to check whether the application complies with the guidelines.

The game server records the following information in the API call log.

  • The principal ID of the user who called the function
  • The name of the function that was called
  • The time of the call (in UTC time)

The function names recorded in the call log are the names used by the game server and are different from the names used by the application to call the functions. For more information about the correspondence between the function names in the call log and the names the application actually uses to call the functions, see 9.5. Function Name Correspondence Tables.

Note that the call log also includes the functions that were called automatically inside the library at times like when logging in to the game server and performing NAT traversal.

9.2.1. Enabling and Disabling the Feature to Record API Calls

Code 9.1. Enabling and Disabling the Feature to Record API Calls
// Enable recording.
bool EnableApiRecorder(ProtocolCallContext* pContext);

// Disable recording.
bool DisableApiRecorder(ProtocolCallContext* pContext);

The call to DebugClient::EnableApiRecorder() enables the recording of API calls. When the feature to record API calls is enabled, the game server stores a log of up to 1,000 API calls using the first in, first out method. Each log is retained for up to 24 hours.

The call to DebugClient::DisableApiRecorder() disables the recording of API calls.

API call logging is disabled by default. Even when API call logging is enabled, it is automatically disabled after 24 hours have elapsed with no API calls to the game server. When the feature is disabled, the log maintained up to that time is invalidated.

Note that the feature to record API calls is a setting that is applied to the whole game server, so the operations of other users can change whether it is enabled.

9.2.2. Getting the API Call Log

To get the API call log recorded in the game server, use the DebugClient::GetApiCalls() function.

Code 9.2. Getting the API Call Log
// Get the recording.
bool GetApiCalls(ProtocolCallContext *pContext,
                  qList<ApiCallData>* pApiCallDatas,
                  qList<PrincipalID>& principalIds,
                  DateTime sinceTime = DateTime::Never,
                  DateTime untilTime = DateTime::Never
                  );

You can get the API call log for all users by passing an empty list in the principalIds parameter. To get the log for a particular user, specify the principal ID of the user whose log you want to get.

To get the log for a specific period of time, specify values for the sinceTime and untilTime parameters. Use sinceTime to specify the start of the period you are getting a summary for. If you specify DateTime::Never for sinceTime, you get a log of all API calls recorded in the game server until the time set for untilTime). Use untilTime to specify the end of the period you are getting a summary for. If you specify DateTime::Never for untilTime, you get a log of all API calls recorded by the server until the current time (rounded to the millisecond).

Note that the log does not include the times set for sinceTime and untilTime. For example, if you specified 2012-04-27 13:00:30 for sinceTime, you would get log entries starting from 2012-04-27 13:00:31.

If the asynchronous process is successful, the log is stored in pApiCallDatas. The log is sorted according to the order in which calls were made.

9.2.3. API Call Log Summary

Use the DebugClient::GetApiCallSummary() function to summarize the call log and check whether the frequency of API calls exceeds the frequency stipulated in the guidelines. For more information, see the Nintendo Switch Guidelines.

9.2.3.1. Getting the API Call Summary

To get a summary of the API calls logged in the game server, use the DebugClient::GetApiCallSummary() function. To get a log summary, the recording of API calls must be enabled, as described in 9.2.1. Enabling and Disabling the Feature to Record API Calls.

Code 9.3. Getting an API Call Summary
// Get the recording.
bool GetApiCallSummary(ProtocolCallContext *pContext,
                        qList<ApiCallSummary>* pApiCallSummaryList,
                        PrincipalID principalId,
                        DateTime sinceTime = DateTime::Never,
                        DateTime untilTime = DateTime::Never,
                        bool isLimitOverOnly = true
                        );

To get the summary for a specific period of time, specify the sinceTime and untilTime parameters. The summary period specified using sinceTime and untilTime works the same as the period specified by those parameters in the GetApiCalls() function.

If you only want to get summaries for API calls that exceed the call frequency limit in the guidelines, specify the isLimitOverOnly parameter. Specify true for this parameter to get summaries only for API calls that are called more frequently than the limit stipulated in the guidelines. Specify false to get summaries for all API calls, including those that do not exceed the limit in guidelines.

If the asynchronous process is successful, the summary is stored in pApiCallSummaryList.

9.2.3.2. Checking the API Call Summary

The ApiCallSummary with the summarized results includes the following information.

  • The name of the function for which the call count has been summarized
  • Whether the limit has been exceeded
  • The standard number of calls stipulated in the limit
  • The standard period stipulated in the limit
  • The time when the period exceeding the limit started
  • The number of calls during the period exceeding the limit
  • The total number of all function calls for the entire time period

Figure 9.1. Information Included in the API Call Summary

The function name obtained by ApiCallSummary::GetMethodName() is the name as used internally by the game server. For more information about the correspondence with the names of functions called by the application, see 9.5. Function Name Correspondence Tables.

Use ApiCallSummary::GetLimit() and ApiCallSummary::GetPeriod() to get the standard number of calls and the standard period that together describe the call frequency limit for the API function for which you have the call count summary.

As reference information, ApiCallSummary also stores data as a time series showing the period when the limit was first exceeded and the number of calls to the function during that period. To get the start time of the period during which API functions were called in excess of the guideline frequency, use the ApiCallSummary::GetCallStartTime() function. To get the number of API calls over a standard time period starting from that time, use the ApiCallSummary::GetCount() function.

Note:

If you specify false for the isLimitOverOnly parameter when you call GetApiCallSummary, the summary you get includes summaries of functions that do not exceed the API call frequency limit. For summaries of functions that do not exceed the API call frequency limit, the return value of the ApiCallSummary::GetResult() function is DebugConstants::ApiCallSummaryResult_Normal. In this case, the information obtained by the ApiCallSummary::GetCallStartTime(),ApiCallSummary::GetCount() function is the start time of the period when calls to the function were most frequent (as opposed to the period when the limit was exceeded), and the number of function calls during that period.

9.3. Changing Game Server Functionality

You can change the behavior of the game server to use it for debugging purposes.

9.3.1. Changing the Setting to Exclude Specific Matchmaking Sessions When Auto-Matchmaking

When the MatchmakeExtensionClient::AutoMatchmake() function is used for auto-matchmaking, there is problem where the user may end up joining the same matchmaking session over and over because the P2P connection could not be established for a reason such as a failure of NAT transversal that causes the auto-matchmaking process to repeat. To avoid this problem, the game server excludes the matchmaking sessions that the user joined in the past from the auto-matchmaking target for the user. Specifically, the game server checks the last three matchmaking sessions where the user participated using auto-matchmaking, and excludes the matchmaking sessions that the user participated in within the last hour from the auto-matchmaking target. This feature is enabled by default.

The participation record used by this feature does not include the matchmaking sessions created by the user and joined by the user.

If you want to use auto-matchmaking and join the same matchmaking session multiple times for application debugging purposes, use the DebugClient::SetExcludeJoinedMatchmakeSession() function to change this exclusion setting. This setting can also be configured using NMAS.

The exclusion setting is applied to the whole game server. Note that when you change the setting, it can affect other developers connected to the same game server. Also note that you cannot change this setting in the production environment game server. (The exclusion setting is always enabled, restricting redundant participation in the same matchmaking session.) For this reason, do not develop your application on the assumption that the exclusion setting will be disabled.

9.4. Error Simulation

Features for error simulation are provided for debugging purposes. With this error simulation feature you can intentionally generate errors when the user calls functions that instigate communication with the game server. Use it o check whether you application is properly handling the errors of the NEX API.

With this error simulation feature, you can specify the principal ID of the user and the name of the function that generates the error, and register the number times the error will occur. You can also register the error simulation settings for numerous API functions for a single principal ID.

The following are examples of error simulation settings.

  • Return QERROR(DataStore, InvalidArgument) every time DataStoreClient::SearchObject() is called.
  • Set so the MatchmakeExtensionClient::BrowseMatchmakeSession() function returns QERROR(Core, Unknown) the first time it is called, returns QERROR(Core, InvalidArgument) the second time, and works normally on the third and subsequent calls.

9.4.1. Error Simulation Settings

The following items can be configured for the error simulation settings.

  • Principal ID
    The principal ID of the user that is the target of error simulation.
  • Function name
    The name of the function that is the target of error simulation. Note that function name specified for error simulation is the name used by the game server, and it differs from the name used by the application for the function. For more information about the correspondence between the function names used by the game server and the function names used by the application, see 9.5. Function Name Correspondence Tables.
  • Validity period
    The period during which the error simulation settings remain valid. When the validity period expires, the error simulation settings are automatically deleted from the game server. The default validity period is one hour.
  • Result
    Specifies the result to return to the user. If a result indicating an error has been specified, the game server returns the error to the user and does not execute the process of the function. If a result indicating success has been specified, or if nothing has been specified for this setting, the game server executes the process of the function in the normal way. But even in this case, an error might be returned if the process does not end normally.
  • Number of times
    Specifies the number of times to return the specified result. If you want to continue to return the same error every time the function is called, specify a large value for this setting. If you want to change the error after a function has been called a certain number of times, set that number here.

You can specify multiple combinations of Result and Number of times settings. If you want to switch the error that is returned to the user depending on the number times that the function has been called, configure the combinations to fit the error sequence that you have in mind.

Note:

When you configure error simulation, be careful not to set combinations of functions and results that would never actually arise. If you specify a result indicating an error, that error is generated regardless of whether it would ever actually occur.

9.4.2. Error Simulation Execution Log

The game server keeps an error simulation execution log that records when errors are simulated when users call specific API functions. This log contains the following information.

  • The name of the function for which an error was simulated.
  • The time when the error was simulated.
  • The result that was returned to the user.

The error simulation execution log is valid for 24 hours from the time of recording. When the validity period expires, the execution log is deleted from the game server.

9.5. Function Name Correspondence Tables

These tables show the correspondence between the names of the functions in the NEX library API and the names of the functions processed by the game server.

These correspondence tables are used for the features described in 9.2. Recording a Log of API Calls and 9.4. Error Simulation.

The table has the following columns.

  • Library Function
    The NEX library function called by the application when it uses NEX. Depending on the overload being used, the server might call different functions even though the library function name is the same. Coding describes the conditions for functions that are called on the server independent of any particular function call by the application.
  • Recorded Library Function Name
    The name used with the API call log feature to display the NEX library function corresponding to the logged server function name. This name is sometimes shown when you use the API call logs with WebAPI or NMAS.
  • Server Function Name
    The name of the function that is actually called by the game server when the application calls a library function. To use the error simulation feature, you must specify this function name to simulate an error for a specific function.
